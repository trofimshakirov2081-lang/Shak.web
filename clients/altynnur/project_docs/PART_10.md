# Часть 10. Финальная архитектура, разработка, тестирование, запуск, передача

## Назначение
Сводит части 1-9 в один реальный продукт (не макет): публичный сайт, админка, CMS, курсы и расписание, дизайн, визуальный редактор, заявки, квиз, CRM, интеграции, SEO, auth, защита данных, резервные копии, история, аналитика, мобильная версия. Плюс порядок разработки, тесты, документация, запуск, передача, приоритеты.

## Анализ перед разработкой (§2)
Читать все части как одно ТЗ, составить карту требований (публичная часть, админка, БД, auth, контент, дизайн, SEO, заявки, интеграции, безопасность, тесты, развёртывание), выявить противоречия, ограничения, зависимости. Нереализуемое выбранной технологией не имитировать: предложить рабочую альтернативу.

## Стек (§3)
Выбор обосновать: производительность, поддержка, расширяемость, безопасность, БД, администрирование, развёртывание, **стоимость эксплуатации**, развитие. Без сложности ради моды. Возможный стек: React (или обоснованный вариант), TypeScript, CSS Modules / Tailwind / своя дизайн-система, Supabase или альтернатива, PostgreSQL, Storage, Auth, серверные функции, Netlify или аналог.
**ПДн россиян: обязательно проверить место хранения**; если сервис не подходит, альтернатива с подходящим размещением БД. LocalStorage только для некритичных настроек.

## Модули (§4)
Public Website, Admin Panel, CMS, Design System, Content Management, Course Management, Lead Management, Quiz Engine, Media Management, SEO Engine, Authentication, API Layer, Database Layer, Notification System, Backup System, Analytics. Чёткая ответственность, без файлов на тысячи строк, логика, UI, БД и стили раздельно, переиспользуемые компоненты.

## Сущности БД (§5, сводный список)
`users`, `roles`, `permissions`, `pages`, `page_blocks`, `block_templates`, `design_settings`, `design_presets`, `courses`, `course_categories`, `course_modules`, `course_lessons`, `teachers`, `schedules`, `reviews`, `gallery_items`, `before_after_items`, `faqs`, `advantages`, `promotions`, `contacts`, `media`, `leads`, `lead_notes`, `lead_status_history`, `quiz_questions`, `quiz_answers`, `quiz_sessions`, `quiz_recommendations`, `integrations`, `notification_queue`, `notification_logs`, `analytics_events`, `seo_settings`, `redirects`, `audit_logs`, `backups`, `legal_documents`, `consent_records`.
Для каждой: PK, связи, обязательные и необязательные поля, типы, ограничения, индексы, права, правила удаления. FK и целостность. **Миграции в файлах проекта**, схема воспроизводима, не только ручные правки в панели Supabase.
(Имена немного отличаются от Ч5 и Ч6: `course_topics`/`course_lessons`, `course_batches`/`schedules`, `gallery_images`/`gallery_items`, `media_files`/`media`. Свести в MASTER.)

## Публичный сайт (§6)
Контент из БД; не хардкодить названия, цены, даты, контакты, отзывы, FAQ, преимущества, фото, описание преподавателя, навигацию, дизайн. Исключение: базовые технические элементы и резервные значения. Публикуется актуальное, черновики не утекают.

## Админка (§7-8)
Разделы: Обзор, Редактор сайта, Страницы, Блоки, Курсы, Категории, Программы, Преподаватели, Расписание, Галерея, Работы, Отзывы, FAQ, Акции, Заявки, CRM, Медиатека, Дизайн, Анимации, SEO, Контакты, Интеграции, Юридические документы, Пользователи, История изменений, Резервные копии, Настройки. Простые термины, подсказки.
Владелица меняет: тексты, заголовки, фото, видео, ссылки, цены, курсы (добавить, удалить), программы, даты, преподавателей, отзывы, FAQ, контакты, цвета, шрифты, скругления, прозрачность, Liquid Glass, анимации, порядок, добавление, удаление, скрытие, дублирование блоков, структуру страницы, предпросмотр, черновик, публикацию, откат к версиям.
**Порядок блоков реально меняет порядок на сайте: если первым стоят контакты, страница начинается с контактов, а не с Hero.**

## Редактор страниц и inline (§9-10)
Поток: открыть страницу → список блоков → порядок → выбрать блок → содержимое → вид → адаптив → черновик → предпросмотр → публикация. Два режима (структурный и визуальный) на одних данных, не две системы. Inline: режим редактирования → подсветка при наведении → клик по тексту, фото, кнопке → редактор → предпросмотр → черновик → публикация.

## Публикация (§11)
Состояния Published, Draft, Preview, Archived. Видно, что опубликовано, а что нет. Автосохранение, ручное сохранение, предпросмотр, публикация, отмена, история версий, восстановление. Публично только опубликованное, предпросмотр защищён.

## Заявки и CRM (§12)
Сквозной сценарий: страница курса → «Записаться» → курс в форме → контакты → согласие → серверная проверка → сохранение → уведомление → CRM → связь. Квиз: ответы сохраняются, рекомендация соответствует, переход к заявке, результат вместе с заявкой. Сбой интеграции не теряет заявку.

## Интеграции (§13)
WhatsApp (диалог с заготовкой, не считать отправкой заявки), Telegram (серверные уведомления через бота), email, Яндекс Метрика, Google Analytics при необходимости. У каждой: настройки, проверка подключения, статус, лог ошибок, отключение, безопасные ключи. Не показывать «подключено», если не работает.

## Аналитика (§14)
Просмотры страниц и курсов, клики CTA, старт и завершение квиза, отправка форм, переходы в WhatsApp и Telegram, источники, UTM. Только реальные данные. Разделять заявки, уникальных посетителей, отправленные уведомления, переходы в мессенджеры, завершённые квизы. Клик по кнопке не равен заявке.

## Тестирование (§15-17)
- Страницы: главная, каталог, курсы, программы, преподаватель, галерея, отзывы, FAQ, контакты, политика, 404. Ссылки, кнопки, серверная логика форм, пустые разделы не выглядят сломанными.
- Ширины: **320, 360, 375, 390, 414, 768, 1024, 1280, 1440, 1920**. Проверить горизонтальный скролл, переносы, фото, кнопки, меню, формы, карточки, галереи, таблицы, админку, визуальный редактор.
- Автотесты: unit, integration, E2E, API, auth, права, формы, публикация, адаптив.
- Минимальные E2E (15): 1 главная; 2 курс; 3 заявка; 4 заявка в CRM; 5 вход админа; 6 правка текста; 7 в черновике; 8 публикация; 9 сайт показывает новое; 10 смена порядка блоков; 11 порядок виден публично; 12 новый курс; 13 курс в каталоге после публикации; 14 без входа нет доступа к CRM; 15 сбой уведомления не удаляет заявку.

## Качество кода (§18)
Без дублирования логики, типы, обработка ошибок, безопасность, производительность, доступность, читаемость, структура, без мёртвого кода и временных костылей. ESLint, TypeScript. Без критических TODO; отложенное явно отмечать.
