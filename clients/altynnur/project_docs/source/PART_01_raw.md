* Белебей.

4. ГЛАВНЫЕ ПРИНЦИПЫ РАЗРАБОТКИ

4.1. Не делать одноразовый сайт

Архитектура должна предусматривать дальнейшее развитие.

В будущем владелица должна иметь возможность:

* Добавлять новые направления обучения.
* Создавать новые курсы.
* Удалять устаревшие курсы.
* Создавать дополнительные страницы.
* Добавлять акции.
* Публиковать новости.
* Добавлять новые фотографии.
* Размещать видео.
* Добавлять преподавателей.
* Создавать дополнительные формы.
* Добавлять новые разделы.
* Менять структуру главной страницы.

Для этого не должно требоваться переписывание сайта.

4.2. Не привязывать контент к исходному коду

Максимально возможное количество информации должно храниться отдельно от программного кода.

Например:

Название курса не должно быть прописано непосредственно в HTML.

Цена курса не должна находиться внутри JavaScript-компонента.

Фотография не должна быть жёстко привязана к конкретному блоку.

Контакты, ссылки, отзывы, даты наборов, тексты, настройки оформления и другие данные должны поступать из системы хранения.

Это необходимо для того, чтобы владелица могла самостоятельно управлять сайтом через админку.

4.3. Модульность

Каждый самостоятельный функциональный элемент должен быть отдельным модулем или компонентом.

Не создавай один огромный файл, в котором находится вся логика сайта.

Разделяй:

* Публичный интерфейс.
* Административный интерфейс.
* Компоненты.
* Стили.
* Логику обработки данных.
* Подключение базы данных.
* Авторизацию.
* Загрузку файлов.
* SEO.
* Формы.
* Интеграции.

Любое изменение одного компонента не должно случайно ломать остальные.

4.4. Масштабируемость

Необходимо предусмотреть возможность добавления новых функций без глобальной переработки архитектуры.

Например, если впоследствии потребуется добавить:

* Онлайн-оплату.
* Личный кабинет ученицы.
* Расписание занятий.
* Бронирование мест.
* Промокоды.
* Реферальную программу.
* Сертификаты в электронном виде.
* Систему уведомлений.

Архитектура должна позволять развивать проект.

Не нужно реализовывать всё перечисленное прямо сейчас. Нужно предусмотреть возможность расширения.

5. ТЕХНОЛОГИЧЕСКАЯ АРХИТЕКТУРА

Основной формат разработки: HTML, CSS и JavaScript.

Однако не ограничивайся исключительно статической HTML-страницей.

Нужна полноценная архитектура с динамическим контентом и серверной частью.

Предлагаемый стек:

FRONTEND:

* HTML5.
* CSS3.
* JavaScript.
* При необходимости React для сложных интерактивных компонентов.
* Современная компонентная архитектура.
* Адаптивная вёрстка.

BACKEND И ХРАНЕНИЕ:

* Supabase в качестве основной платформы backend.
* PostgreSQL для структурированных данных.
* Supabase Storage для фотографий, видео и других файлов.
* Supabase Auth для авторизации администратора.
* Row Level Security для ограничения доступа к данным.

HOSTING:

* Netlify или аналогичная платформа для размещения публичной части.
* Возможность подключения собственного домена.

Важно: окончательно выбери архитектуру с учётом надёжности, стоимости эксплуатации и удобства обслуживания.

Не используй исключительно LocalStorage для хранения основного контента.

LocalStorage можно использовать для временных пользовательских настроек, но не как основное хранилище сайта.

Не храни пароли администратора в открытом виде в JavaScript, HTML, CSS или публичных конфигурационных файлах.

Секретные ключи должны находиться только в защищённой серверной среде.

Публичный сайт должен корректно работать даже после обновления страницы, перехода по прямой ссылке и очистки кэша браузера.

Все изменения, опубликованные через админку, должны сохраняться в постоянном хранилище.

Если информация отсутствует, показывать аккуратную заглушку или скрывать соответствующий элемент.

Не отображать пустые поля, слова undefined, null и технические значения.

АДМИНИСТРИРОВАНИЕ КУРСОВ:

Нужна полноценная система управления каталогом.

Администратор должен иметь возможность:

* Создавать курсы.
* Удалять курсы.
* Редактировать существующие курсы.
* Дублировать курсы.
* Менять названия.
* Менять описания.
* Менять фотографии.
* Загружать несколько фотографий.
* Менять стоимость.
* Указывать старую стоимость.
* Указывать скидку.
* Добавлять продолжительность.
* Выбирать формат обучения.
* Указывать количество мест.
* Указывать даты набора.
* Добавлять программу обучения.
* Добавлять список навыков.
* Добавлять информацию о материалах.
* Указывать, предоставляются ли модели.
* Добавлять информацию о сертификате.
* Указывать возможность рассрочки.
* Добавлять дополнительные преимущества.
* Настраивать кнопку записи.
* Скрывать курс.
* Публиковать курс.
* Перемещать курс выше или ниже остальных.

Предусмотреть статусы:

* Черновик.
* Опубликован.
* Набор открыт.
* Набор закрыт.
* Архивный.

Архивные курсы не должны отображаться в основном каталоге, но должны сохраняться в админке.

Каждый курс должен иметь уникальный идентификатор.

В будущем должна быть возможность создавать отдельные страницы курсов с подробной программой обучения.

12. ОБЩИЙ ПРИНЦИП РАБОТЫ ВСЕХ БЛОКОВ

Каждый блок сайта должен быть самостоятельной управляемой единицей.

Необходимо заложить единую архитектуру блоков.

У каждого блока должны быть:

* Уникальный ID.
* Название.
* Тип блока.
* Статус отображения.
* Позиция на странице.
* Содержимое.
* Настройки внешнего вида.
* Настройки адаптивности.
* Дата последнего изменения.

Необходимо предусмотреть единый механизм управления блоками, а не создавать отдельную систему для каждого раздела.

Подробную реализацию универсального конструктора блоков, визуального редактора, предпросмотра и системы публикации необходимо разработать в рамках последующих требований.

13. ГЛАВНОЕ ТРЕБОВАНИЕ К РЕЗУЛЬТАТУ ПЕРВОГО ЭТАПА

Не приступай к случайному созданию всех блоков в одном файле.

Сначала проанализируй архитектуру проекта.

Определи:

1. Какие компоненты необходимы.
2. Какие таблицы потребуются в базе данных.
3. Какие данные должны храниться в базе.
4. Как будет происходить взаимодействие сайта с базой данных.
5. Как будет устроена авторизация.
6. Как будут загружаться фотографии и видео.
7. Как будет работать административная панель.
8. Как обеспечить независимость контента от программного кода.
9. Как обеспечить безопасность.
10. Как обеспечить дальнейшее расширение функциональности.

После этого создай основу проекта.

Не заменяй полноценную реализацию имитацией интерфейса.

Если кнопка существует, она должна выполнять предусмотренное действие.

Если предусмотрен редактор, он должен действительно сохранять изменения.

Если предусмотрено скрытие блока, блок должен исчезать на публичном сайте.

Если предусмотрено изменение порядка блоков, порядок должен сохраняться после перезагрузки.

Если предусмотрена загрузка фотографии, файл должен действительно загружаться в хранилище.

Все основные решения документируй.

Приоритет: надёжная архитектура, реальная работоспособность и удобство дальнейшей разработки.
