
38. ГЛАВНАЯ КОНЦЕПЦИЯ АДМИНИСТРАТИВНОЙ ПАНЕЛИ

Создай полноценную систему управления сайтом (CMS).

Административная панель должна стать самостоятельным продуктом внутри сайта.

Это не должна быть обычная страница с несколькими полями ввода.

Нам нужна визуальная, функциональная и максимально понятная система управления всеми элементами сайта.

Владелица учебного центра не обязана знать:

* HTML.
* CSS.
* JavaScript.
* React.
* SQL.
* Принципы работы баз данных.
* Принципы веб-разработки.

Она должна выполнять все основные действия через визуальный интерфейс.

Главный принцип:

ЕСЛИ ЭЛЕМЕНТ МОЖНО ИЗМЕНИТЬ НА САЙТЕ, ЕГО ИЗМЕНЕНИЕ ДОЛЖНО БЫТЬ ДОСТУПНО В АДМИНКЕ.

Это относится к:

* Текстам.
* Заголовкам.
* Подзаголовкам.
* Фотографиям.
* Видео.
* Иконкам.
* Ссылкам.
* Кнопкам.
* Ценам.
* Контактам.
* Формам.
* Карточкам.
* Блокам.
* Шрифтам.
* Цветам.
* Фонам.
* Отступам.
* Скруглениям.
* Анимациям.
* Расположению элементов.
* Настройкам отображения.
* Структуре страниц.

Никаких изменений через ручное редактирование исходного кода для стандартных операций.

39. ВХОД В АДМИНИСТРАТИВНУЮ ПАНЕЛЬ

Вход должен быть доступен через малозаметную ссылку в самом низу сайта.

Текст ссылки:

«Админка».

Она должна быть неброской, полупрозрачной и не отвлекать посетителей.

При нажатии открывается отдельная страница авторизации.

Предлагаемый адрес:

/admin

39.1. Страница авторизации

Предусмотреть:

* Логин или электронную почту.
* Пароль.
* Кнопку входа.
* Возможность показать или скрыть пароль.
* Восстановление доступа.
* Сообщения об ошибках.
* Индикатор загрузки.

Не показывать технические ошибки пользователю.

При неправильном пароле выводить понятное сообщение.

39.2. Безопасность авторизации

Обязательно:

* Использовать Supabase Auth или эквивалентную защищённую систему.
* Не хранить пароль в открытом виде.
* Не размещать секретные ключи в клиентском коде.
* Ограничивать количество попыток входа.
* Использовать защищённые сессии.
* Реализовать выход из аккаунта.
* Проверять права доступа на серверной стороне.
* Защищать административные запросы.
* Использовать Row Level Security.

Скрытый адрес админки не является защитой.

39.3. Управление доступом

На первом этапе достаточно одного основного администратора.

Но архитектура должна предусматривать добавление дополнительных пользователей.

В будущем можно реализовать роли:

* Владелец.
* Администратор.
* Редактор.
* Наблюдатель.

Владелец имеет полный доступ.

Администратор может управлять контентом и заявками.

Редактор может менять тексты, изображения и блоки.

Наблюдатель может только просматривать информацию.

Необязательно реализовывать все роли прямо сейчас, но архитектуру следует предусмотреть.

42. ГЛАВНЫЙ РЕДАКТОР САЙТА

Это центральная функция административной панели.

Создай раздел «Редактор сайта».

Он должен позволять управлять публичным сайтом в визуальном формате.

Предусмотри два основных режима.

РЕЖИМ 1. СПИСОК БЛОКОВ.

Показывает все блоки страницы в виде удобного списка.

РЕЖИМ 2. ВИЗУАЛЬНЫЙ РЕДАКТОР.

Показывает страницу сайта с возможностью выбирать отдельные элементы и переходить к их настройкам.

Оба режима должны быть синхронизированы.

Если пользователь изменил блок в одном режиме, изменения должны отображаться в другом.

43.1. Drag & Drop

После перемещения:

* Изменяется позиция блока.

Предусмотреть визуальное обозначение места, куда будет перемещён блок.

Не допускать случайного перемещения при нажатии на кнопки редактирования.

На мобильных устройствах предусмотреть удобное управление порядком.

Дополнительно реализовать кнопки:

* Переместить выше.
* Переместить ниже.

Это необходимо для устройств, где перетаскивание неудобно.

44. СКРЫТИЕ И ОТОБРАЖЕНИЕ БЛОКОВ

Каждый блок должен иметь переключатель видимости.

Состояния:

* Отображается.
* Скрыт.

При скрытии:

* Блок перестаёт отображаться на публичном сайте.
* Блок остаётся в админке.
* Его содержимое не удаляется.
* Его настройки сохраняются.
* Его позиция сохраняется.

При повторном включении блок возвращается в прежнее положение.

Предусмотреть визуальные обозначения скрытых блоков.

Например:
«Скрыт на сайте».

45. УДАЛЕНИЕ И ДУБЛИРОВАНИЕ

* Редактировать.
* Дублировать.
* Скрыть.
* Удалить.

45.1. Дублирование

При дублировании создаётся новый блок с:

* Новым уникальным ID.
* Копией содержимого.
* Копией настроек.
* Независимым статусом видимости.
* Независимой позицией.

Изменение копии не должно менять оригинал.

45.2. Удаление

Перед удалением показывать подтверждение.

Например:

«Вы действительно хотите удалить этот блок?»

Предусмотреть возможность отмены удаления через историю изменений.

Не удалять связанные медиафайлы автоматически, если они используются в других местах.

48. ВИЗУАЛЬНОЕ ВЫДЕЛЕНИЕ ЭЛЕМЕНТОВ

Например:

* Заголовок.
* Кнопку.
* Фотографию.
* Карточку.
* Текст.
* Фоновый элемент.

После выбора элемента открываются его настройки.

Визуально выбранный элемент выделяется рамкой.

При наведении можно показывать название элемента.

Предусмотреть подсказки:

* «Изменить текст».
* «Заменить фотографию».
* «Изменить ссылку».
* «Настроить внешний вид».

При этом не превращай редактор в сложную профессиональную программу.

Основной пользователь должен понимать, куда нажимать.

49. ПРЕДПРОСМОТР ИЗМЕНЕНИЙ

Одна из обязательных функций.

Перед публикацией администратор должен видеть, как сайт будет выглядеть после изменений.

Предусмотреть:

* Предпросмотр всей страницы.
* Предпросмотр отдельного блока.
* Предпросмотр мобильной версии.
* Предпросмотр планшетной версии.
* Предпросмотр десктопной версии.

Изменения должны отображаться без необходимости публиковать их на рабочем сайте.

Для этого используй систему черновиков.

Предусмотреть кнопку:

«Предпросмотр».

Предпросмотр должен показывать именно текущие неопубликованные изменения.

Публичные посетители не должны видеть черновики.

50. СОХРАНЕНИЕ И ПУБЛИКАЦИЯ

Разделить два действия:

1. Сохранить изменения.
2. Опубликовать изменения.

СОХРАНИТЬ:

Изменения записываются в черновик.

Публичный сайт остаётся без изменений.

ОПУБЛИКОВАТЬ:

Новые данные становятся доступными посетителям.

Перед публикацией показывать краткое описание:

«Вы собираетесь опубликовать изменения сайта».

Дополнительно предусмотреть:

* Автосохранение черновиков.
* Индикатор несохранённых изменений.
* Восстановление после случайного закрытия страницы.
* Проверку обязательных данных.
* Предупреждение о возможных ошибках.

Не публиковать частично сохранённые изменения.

Публикация должна быть атомарной с точки зрения отображаемого контента: посетитель должен получать согласованную версию сайта.

51. ПЕРЕМЕЩЕНИЕ ЦЕЛЫХ СТРАНИЦ

Архитектура должна поддерживать не только одну главную страницу.

Предусмотреть полноценную систему страниц.

Например:

* Главная.
* Все курсы.
* Отдельные курсы.
* О преподавателе.
* Галерея.
* Контакты.
* Политика конфиденциальности.

В админке должен быть раздел «Страницы».

Владелица может:

* Создавать страницы.
* Удалять страницы.
* Менять названия.
* Менять URL.
* Менять порядок.
* Скрывать страницы.
* Публиковать страницы.
* Создавать копии.
* Выбирать шаблон.
* Управлять SEO.

У каждой страницы собственный набор блоков.

Главная страница не должна быть жёстко привязана к определённой позиции в системе.

Предусмотреть возможность менять порядок страниц в навигации.

Важно: перемещение страницы в навигации не должно менять её URL автоматически.

52. СИСТЕМА ШАБЛОНОВ

Предусмотреть библиотеку шаблонов блоков.

Например, для блока отзывов можно иметь несколько вариантов:

* Карточки.
* Слайдер.
* Список.
* Большие отзывы с фотографиями.

Для каталога:

* Сетка из трёх карточек.
* Сетка из двух карточек.
* Компактный список.
* Горизонтальная карусель.

Для преимуществ:

* Карточки с иконками.
* Карточки с фотографиями.
* Горизонтальный список.

Пользователь выбирает нужный вариант без изменения данных.

При переключении шаблона данные не должны теряться.

53. УПРАВЛЕНИЕ ВИДИМОСТЬЮ ЭЛЕМЕНТОВ

Помимо скрытия целых блоков, нужно предусмотреть управление отдельными элементами.

Например:

В первом экране можно отдельно скрыть:

* Подзаголовок.
* Первую кнопку.
* Вторую кнопку.

* Дополнительный текст.

В карточке курса:

* Цену.
* Старую цену.
* Дату.
* Продолжительность.
* Кнопку.
* Изображение.

У каждого управляемого элемента должен быть переключатель видимости, если это имеет смысл для данного типа компонента.

54. СИСТЕМА ПРЕДУПРЕЖДЕНИЙ

Добавь в админку центр уведомлений о состоянии сайта.

Примеры:

* Не заполнен адрес учебного центра.
* Не добавлена фотография преподавателя.
* У курса отсутствует описание.
* Не указана продолжительность.
* Есть неопубликованные изменения.
* Не добавлена политика конфиденциальности.
* Отсутствует SEO description.
* Есть блок без изображения.

Предусмотреть приоритеты:

* Критично.
* Важно.
* Рекомендация.

При нажатии на уведомление пользователь должен попадать в соответствующий редактор.

Не блокировать публикацию из-за необязательных полей.

Но критические проблемы, например неработающая форма заявки или отсутствие необходимого согласия, должны блокировать публикацию соответствующей функциональности.

55. ПОИСК ПО АДМИНКЕ

Добавь глобальный поиск.

Пользователь вводит запрос, например:

«Цена курса бровей».

Система должна находить:

* Соответствующий курс.
* Поле цены.
* Страницу, где курс отображается.
* Возможность быстро перейти к редактированию.

Также предусмотреть поиск:

* По страницам.
* По блокам.
* По курсам.
* По отзывам.
* По фотографиям.
* По настройкам.

Это значительно упростит работу с сайтом при увеличении количества контента.

56. УДОБСТВО И ИНТЕРФЕЙС

Админка должна выглядеть как современная программа управления.

Не делай её похожей на техническую панель разработчика.

Основные принципы:

* Чистый интерфейс.
* Понятные подписи.
* Умеренное количество цветов.
* Логичная структура.
* Хорошая читаемость.
* Большие удобные области нажатия.
* Понятные иконки.
* Подсказки.
* Подтверждения важных действий.

Для сложных функций добавляй небольшие пояснения.

Например:

«Скрыть блок» — блок останется в админке, но перестанет отображаться посетителям.

Не используй технические термины там, где можно объяснить простыми словами.

57. МОБИЛЬНАЯ ВЕРСИЯ АДМИНКИ

Обязательно разработай мобильную версию административной панели.

Владелица должна иметь возможность управлять сайтом с телефона.

Проверить:

* Вход.
* Редактирование текста.
* Загрузку фотографий.
* Изменение цен.
* Добавление отзывов.
* Изменение дат.
* Скрытие блоков.
* Перемещение блоков.
* Публикацию.

Не просто сжимай десктопную панель.

На мобильном устройстве используй:

* Компактную навигацию.
* Выдвижное меню.
* Удобные карточки.
* Полноэкранные редакторы.
* Крупные кнопки.
* Удобные переключатели.

Drag & Drop должен иметь альтернативу в виде кнопок перемещения.

58. ТРЕБОВАНИЯ К СОХРАННОСТИ ДАННЫХ

Нельзя допускать потерю данных при случайном закрытии админки.

Предусмотреть:

* Автосохранение черновиков.
* Обработку ошибок соединения.
* Повторную отправку неудачных запросов.
* Индикатор состояния сохранения.
* Проверку успешной записи в базу.
* Резервные копии.

Если соединение пропало во время редактирования, пользователь должен получить понятное уведомление.

Не показывать сообщение «Сохранено», пока данные фактически не сохранены.

59. ИТОГОВЫЕ ТРЕБОВАНИЯ

Административная панель должна быть полноценной CMS.

Основные возможности:

1. Редактирование сайта.
2. Управление страницами.
3. Управление блоками.
4. Drag & Drop.
5. Скрытие и отображение.
6. Добавление блоков.
7. Удаление блоков.
8. Дублирование блоков.
9. Изменение содержимого.
10. Изменение отдельных элементов.
11. Предпросмотр.
12. Черновики.
13. Публикация.
14. Управление шаблонами.
15. Поиск.
16. Уведомления.
17. Мобильная версия.
18. Автосохранение.

Все действия должны быть реально работающими.

Не создавай имитацию админки с кнопками, которые не выполняют никаких действий.

Все данные должны сохраняться в базе.

После выхода и повторного входа все изменения должны оставаться.

Публичный сайт должен получать актуальную опубликованную версию.

Черновики должны оставаться приватными.

Главная задача: сделать систему, в которой владелица может самостоятельно управлять структурой сайта, не обращаясь к разработчику.
