ЧАСТЬ 8. БЕЗОПАСНОСТЬ, ЮРИДИЧЕСКИЕ ДОКУМЕНТЫ, РЕЗЕРВНОЕ КОПИРОВАНИЕ И НАДЕЖНОСТЬ

1. Главная задача

Реализуй полноценную систему безопасности и надежности для сайта учебного центра «АлтынНур».

Это не просто публичный сайт. Проект содержит:

* Публичную часть.
* Административную панель.
* Базу данных.
* Систему авторизации.
* Заявки клиентов.
* Контактную информацию.
* Фотографии и видеоматериалы.
* Интеграции с мессенджерами.
* Настройки дизайна.
* Систему публикации.
* Историю изменений.

Все эти компоненты должны быть защищены.

Главная цель: владелица должна спокойно пользоваться сайтом, не опасаясь случайно удалить данные, потерять заявки или открыть посторонним доступ к управлению.

Не создавай фиктивную безопасность. Все механизмы должны реально работать.

2. Модель угроз

Перед реализацией учитывай основные риски:

1. Попытки подобрать пароль администратора.
2. Несанкционированный доступ к админке.
3. Получение доступа к заявкам.
4. Утечка контактных данных клиентов.
5. Изменение или удаление контента посторонними.
6. Внедрение вредоносного кода через текстовые поля.
7. Загрузка опасных файлов.
8. Утечка API-ключей.
9. Ошибки в настройках базы данных.
10. Случайное удаление важных материалов владельцем.
11. Потеря данных при сбое хостинга.
12. Ошибки при публикации изменений.
13. Повреждение базы данных.
14. Неправильная настройка доступа к Storage.
15. Злоупотребление публичными формами заявок.

Разрабатывай систему с учетом этих сценариев.

3. Защита административной панели

Административная панель должна иметь настоящую авторизацию.

Недостаточно просто скрыть ссылку на админку или сделать сложный URL.

3.1. Вход

Используй Supabase Auth или другую надежную систему авторизации.

Предусмотри:

* Вход по электронной почте и паролю.
* Восстановление пароля.
* Выход из аккаунта.
* Проверку сессии.
* Защиту закрытых маршрутов.
* Автоматическое истечение сессии по правилам выбранной системы.
* Возможность смены пароля.
* Понятные сообщения об ошибках.

Не храни пароли в открытом виде.

Не реализуй собственную систему хранения паролей, если можно использовать проверенный механизм авторизации.

3.2. Роли и права доступа

На первом этапе основной пользователь - владелица учебного центра.

Предусмотри архитектуру для будущих ролей:

* Владелец.
* Администратор.
* Редактор контента.
* Менеджер заявок.

Для каждой роли должны быть отдельные разрешения.

Например:

Владелец:

* Полный доступ.
* Управление пользователями.
* Управление интеграциями.
* Настройка безопасности.
* Публикация.
* Удаление и восстановление данных.

Редактор:

* Работа с текстами.
* Работа с фотографиями.
* Управление курсами.
* Редактирование страниц.

Менеджер:

* Просмотр заявок.
* Изменение статусов.
* Добавление заметок.
* Связь с клиентами.

Даже если на первом этапе используется только одна учетная запись, архитектура должна позволять расширение.

3.3. Ссылка на админку

Внизу публичного сайта должна быть небольшая малозаметная ссылка «Админка».

При нажатии открывается страница входа.

Но отсутствие ссылки не должно быть частью системы безопасности.

Защита обеспечивается авторизацией, серверными проверками и политиками доступа.

4. Защита базы данных

Если используется Supabase, настрой Row Level Security для всех таблиц, содержащих пользовательские или административные данные.

Не оставляй таблицы открытыми для чтения и изменения из публичного интернета.

Для каждой таблицы определи:

* Кто может читать данные.
* Кто может создавать записи.
* Кто может редактировать.
* Кто может удалять.
* Какие данные доступны публично.
* Какие данные доступны только владельцу.

Особенно тщательно защити:

* leads.
* lead_notes.
* lead_status_history.
* users.
* notification_logs.
* notification_queue.
* integrations.
* admin_settings.
* audit_logs.

Публичный посетитель не должен иметь возможности получить список заявок или прочитать чужие контактные данные.

4.1. Разделение публичных и приватных данных

Публично можно отдавать только информацию, необходимую для отображения сайта:

* Названия курсов.
* Описания.
* Цены, если они опубликованы.
* Даты наборов, если они опубликованы.
* Публичные фотографии.
* Контакты.
* Публичные отзывы.

Не отдавай через API:

* Данные клиентов.
* Внутренние заметки.
* Пароли.
* Токены.
* Секретные ключи.
* Внутренние журналы.
* Скрытые настройки.
* Административную информацию.

Не загружай все данные в браузер с последующим скрытием ненужной информации через CSS или JavaScript.

Приватные данные вообще не должны попадать в публичный frontend.

5. Защита API и секретов

Все секретные ключи должны храниться на серверной стороне или в защищенных переменных окружения.

Никогда не размещай в открытом frontend:

* Supabase service_role key.
* Telegram Bot Token.
* SMTP-пароли.
* Секреты интеграций.
* Приватные API-ключи.
* Ключи доступа к внешним сервисам.

Публичный Supabase anon key допустим только при корректно настроенных RLS и политиках доступа.

Для серверных функций используй защищенные переменные окружения.

Создай файл .env.example, в котором перечислены необходимые переменные без реальных значений.

Добавь .env и другие файлы с секретами в .gitignore.

Перед публикацией проверяй, что секреты не попали в GitHub и собранный frontend.

6. Защита форм заявок

Все формы должны быть защищены от автоматического спама и злоупотреблений.

Реализуй:

* Проверку данных на клиенте.
* Обязательную проверку данных на сервере.
* Ограничение частоты запросов.
* Honeypot-поле.
* Защиту от слишком частых повторных отправок.
* Проверку формата телефона.
* Ограничение длины текстовых полей.
* Нормализацию данных.
* Безопасную обработку ошибок.

При необходимости предусмотрена интеграция CAPTCHA.

Не полагайся исключительно на JavaScript-валидацию.

Все проверки должны выполняться повторно на серверной стороне.

6.1. Защита от повторных заявок

Предусмотри защиту от случайной многократной отправки одной формы.

После отправки:

* Покажи подтверждение.
* Заблокируй повторную отправку на время обработки.
* Не создавай несколько одинаковых заявок из-за повторного нажатия.
* Обрабатывай повторные запросы безопасно.

При этом не блокируй возможность повторного обращения человека в будущем.

7. Безопасная работа с контентом

Все данные, которые владелица вводит в админке, должны безопасно обрабатываться.

Особенно:

* Заголовки.
* Описания.
* Отзывы.
* FAQ.
* Подписи к фотографиям.
* HTML-контент.
* Ссылки.
* SEO-поля.

Защити сайт от XSS.

Не вставляй пользовательский HTML напрямую в DOM без безопасной обработки.

Если предусмотрен визуальный редактор с форматированием текста, используй безопасную очистку разрешенных HTML-тегов.

Запрещай опасные атрибуты и скрипты.

Проверяй внешние ссылки.

Не допускай выполнения JavaScript, введенного через обычные текстовые поля.

8. Безопасная загрузка файлов

Реализуй безопасную загрузку изображений и других разрешенных файлов.

Проверяй:

* Тип файла.
* MIME type.
* Расширение.
* Размер.
* Фактический формат изображения.
* Допустимые размеры.
* Возможность безопасной обработки.

Не доверяй только расширению файла.

Предусмотри ограничения на размер загрузки.

Не разрешай загрузку исполняемых файлов в публичную медиатеку.

Для изображений используй обработку и оптимизацию.

Для Storage настрой отдельные правила доступа:

* Публичные изображения могут отображаться на сайте.
* Приватные файлы доступны только авторизованным пользователям.
* Документы и резервные копии не должны быть публичными.

9. Юридические документы

Подготовь систему юридических страниц.

Необходимо предусмотреть:

1. Политику обработки персональных данных.
2. Согласие на обработку персональных данных.
3. Условия использования сайта, если они необходимы.
4. Согласие на рекламные и информационные рассылки, если они будут использоваться.
5. Дополнительные документы при необходимости.

Все документы должны редактироваться через админку.

Не создавай видимость юридической проверки.

Подготовь структуру и технические механизмы, но оставь возможность проверить тексты с профильным специалистом.

9.1. Политика обработки персональных данных

Подготовь страницу с описанием:

* Кто является оператором персональных данных.
* Какие данные собираются.
* Для каких целей.
* На каком основании.
* Как обрабатываются.
* Где хранятся.
* Кому могут передаваться.
* Как долго хранятся.
* Как пользователь может отозвать согласие.
* Как обратиться по вопросам обработки данных.

Не выдумывай юридическое наименование владельца, ИНН, адрес или другие реквизиты.

Если информации нет, используй явные редактируемые поля-заглушки.

Не публикуй документ с незаполненными обязательными сведениями как окончательно готовый.

9.2. Согласие в формах

Перед отправкой заявки пользователь должен видеть понятное уведомление о персональных данных и ссылку на политику.

Реализуй отдельный checkbox согласия.

Требования:

* Checkbox изначально не отмечен.
* Без обязательного согласия заявка не отправляется.
* Ссылка на документ открывается.
* Текст согласия редактируется через админку.
* Сохраняется факт получения согласия.

Сохраняй вместе с заявкой:

* Дату и время.
* Версию текста согласия.
* Идентификатор документа.
* Факт согласия.
* Необходимые технические сведения о заявке.

Не собирай лишние данные о посетителе.

9.3. Рекламные рассылки

Если в будущем появится рекламная рассылка, сделай отдельное добровольное согласие.

Не объединяй согласие на обработку заявки и согласие на рекламные сообщения.

Не ставь рекламный checkbox автоматически.

9.4. Российское законодательство

Проверь техническую архитектуру с учетом применимых требований российского законодательства о персональных данных, в том числе Федерального закона № 152-ФЗ.

Отдельно проверь:

* Требования к локализации персональных данных.
* Основания обработки.
* Порядок получения согласий.
* Требования к политике обработки персональных данных.
* Передачу данных сторонним сервисам.
* Трансграничную передачу, если она возникает.
* Обязанности оператора.
* Требования к хранению и удалению данных.

Не считай автоматическое подключение иностранного облачного сервиса достаточным подтверждением соответствия законодательству.

До запуска необходимо подтвердить, где физически хранятся персональные данные и как организованы все передачи.

Если выбранный Supabase или другой сервис не позволяет обеспечить необходимые условия, предложи альтернативную архитектуру с подходящим размещением базы данных.

Не отправляй персональные данные в Telegram, почту или другие внешние сервисы без проверки правовых оснований и необходимых настроек.

10. Хранение и удаление заявок

Владелица должна иметь возможность управлять сроками хранения заявок.

Предусмотри:

* Архивирование.
* Удаление.
* Экспорт.
* Поиск.
* Фильтрацию.
* Просмотр истории действий.

Не удаляй заявки автоматически без заранее установленного правила.

Если будет реализовано автоматическое удаление, срок и условия должны быть настраиваемыми и соответствовать утвержденной политике хранения.

При удалении заявки учитывай связанные заметки, события и журналы.

Не сохраняй лишние персональные данные в логах.

11. Резервное копирование

Реализуй систему резервного копирования.

Должна существовать возможность восстановить проект после:

* Случайного удаления курса.
* Ошибки при редактировании.
* Неправильной публикации.
* Повреждения данных.
* Сбоя сервиса.
* Неудачного обновления.

Предусмотри резервное копирование:

* Базы данных.
* Контента.
* Настроек сайта.
* Медиатеки.
* Дизайн-токенов.
* Структуры страниц.
* Настроек интеграций без раскрытия секретов.

Не ограничивайся экспортом JSON в браузере.

Для настоящего резервного копирования используй серверные механизмы, возможности инфраструктуры или отдельное защищенное хранилище.

11.1. Настройки резервного копирования

В административной панели создай раздел «Резервные копии».

Показывай:

* Дату последней копии.
* Статус.
* Размер.
* Тип копии.
* Возможность создать копию вручную.
* Возможность восстановить данные.
* Историю резервных копий.

Автоматическое расписание должно настраиваться с учетом возможностей выбранного хостинга и базы данных.

Если автоматическое резервное копирование не настроено, явно показывай предупреждение.

11.2. Восстановление

Восстановление должно требовать дополнительного подтверждения.

Перед восстановлением текущего состояния создай контрольную копию, если это технически возможно.

Не допускай случайного восстановления старой версии поверх актуальных данных.

После восстановления проверь целостность данных и работу сайта.

12. История изменений и журнал действий

Создай полноценный журнал административных действий.

Фиксируй:

* Вход в админку.
* Выход.
* Создание курса.
* Изменение курса.
* Удаление курса.
* Изменение цены.
* Изменение даты набора.
* Публикацию страницы.
* Изменение дизайна.
* Изменение контактов.
* Изменение настроек интеграций.
* Изменение юридических документов.
* Действия с заявками.
* Восстановление резервной копии.

Для записи сохраняй:

* Тип действия.
* Дату и время.
* Пользователя.
* Объект.
* Измененные поля.
* Предыдущее и новое значение, когда это необходимо.

Не записывай пароли и секретные токены.

Предусмотри фильтрацию истории и поиск.

13. Защита от случайных действий

Админка должна быть безопасной не только технически, но и с точки зрения интерфейса.

Для опасных действий используй подтверждения.

Например:

* Удаление курса.
* Удаление страницы.
* Удаление фотографии.
* Очистка галереи.
* Массовое изменение.
* Публикация большого количества изменений.
* Восстановление резервной копии.

Для особенно опасных действий попроси повторно подтвердить операцию.

Добавь возможность отменить последнее действие там, где это технически возможно.

Предусмотри корзину для удаленных объектов.

Не удаляй важный контент безвозвратно сразу после нажатия кнопки.

14. Черновики и безопасная публикация

Изменения на сайте должны проходить через систему черновиков.

Разделяй:

* Текущую опубликованную версию.
* Черновую версию.
* Предпросмотр.
* Историю опубликованных версий.

При ошибке публикации сайт должен сохранять предыдущую рабочую версию.

Не допускай частичного обновления, когда половина блоков уже опубликована, а другая половина нет.

Используй безопасный механизм публикации с проверкой данных.

Перед публикацией показывай предупреждения о важных ошибках.

15. Мониторинг состояния проекта

Создай в админке раздел состояния сайта.

Показывай доступную информацию:

* Доступность базы данных.
* Состояние авторизации.
* Состояние Storage.
* Последнюю успешную публикацию.
* Последнее резервное копирование.
* Ошибки интеграций.
* Ошибки отправки уведомлений.
* Проблемы с загрузкой файлов.

Не показывай технические секреты.

Если сервис недоступен, отображай понятное сообщение.

Не делай вид, что все работает, если проверка не прошла.

16. Обработка ошибок

Все ошибки должны обрабатываться корректно.

Для посетителя:

* Не показывай технический стек.
* Не раскрывай SQL-запросы.
* Не показывай секретные данные.
* Не выводи внутренние пути сервера.
* Показывай понятное сообщение и возможное действие.

Для администратора:

* Показывай понятную причину.
* Предлагай безопасное действие.
* Сохраняй информацию для диагностики.
* Не раскрывай секреты.

Создай централизованную систему логирования.

Разделяй ошибки frontend, backend и интеграций.

17. Доступность и надежность внешних интеграций

Если Telegram, почта или другие сервисы временно недоступны, сайт не должен переставать принимать заявки.

Логика должна быть следующей:

1. Пользователь отправляет форму.
2. Сервер проверяет данные.
3. Заявка сохраняется в базе.
4. Создается задача на отправку уведомления.
5. Система пытается отправить уведомление.
6. Если отправка не удалась, заявка остается сохраненной.
7. Система записывает ошибку.
8. После восстановления сервиса возможна повторная отправка.

Не связывай сохранение заявки с успешностью Telegram или почты.

18. Безопасность административной сессии

Предусмотри:

* Проверку действительности сессии.
* Защиту закрытых страниц.
* Безопасное завершение сессии.
* Повторную авторизацию для особо опасных операций, если поддерживается выбранной системой.
* Защиту от CSRF там, где она применима.
* Безопасную работу с cookies.
* HTTPS.
* Защиту от перебора паролей средствами выбранной системы авторизации.

Не реализуй небезопасное хранение токенов.

19. HTTPS и домен

Перед запуском на реальном домене обеспечь:

* HTTPS.
* Корректный SSL-сертификат.
* Перенаправление HTTP на HTTPS.
* Единую основную версию домена.
* Отсутствие смешанного контента.
* Корректную работу всех форм и интеграций.

Не допускай передачи контактных данных через незашифрованное соединение.

20. Тестирование безопасности

Проведи проверку основных сценариев.

Проверка доступа

* Неавторизованный пользователь не открывает админку.
* Неавторизованный пользователь не может изменить контент.
* Неавторизованный пользователь не может получить список заявок.
* Пользователь с ограниченной ролью не получает лишних прав.
* Секретные ключи отсутствуют в frontend.

Проверка форм

* Некорректный телефон отклоняется.
* Пустая обязательная форма отклоняется.
* Согласие обязательно.
* Повторная отправка обрабатывается корректно.
* Спам ограничивается.
* Ошибка Telegram не приводит к потере заявки.

Проверка файлов

* Недопустимые форматы отклоняются.
* Превышение размера обрабатывается.
* Приватные файлы недоступны публично.
* Опасный HTML не исполняется.

Проверка резервных копий

* Создается резервная копия.
* Ее можно проверить.
* Восстановление требует подтверждения.
* После восстановления сайт продолжает работать.

Проверка публикации

* Черновик не меняет публичный сайт.
* Предпросмотр работает.
* Ошибка публикации не уничтожает предыдущую версию.
* История изменений сохраняется.

21. Критерии готовности

Считай эту часть реализованной, когда:

1. Админка защищена авторизацией.
2. Есть разграничение ролей.
3. RLS настроен для всех необходимых таблиц.
4. Публичные данные отделены от приватных.
5. Заявки недоступны посторонним.
6. Секреты не попадают во frontend.
7. Формы защищены от основных видов спама.
8. Пользовательский контент безопасно обрабатывается.
9. Загрузка файлов защищена.
10. Юридические страницы созданы как редактируемые сущности.
11. Согласие на обработку данных реализовано.
12. Рекламное согласие отделено от основного.
13. Предусмотрено управление хранением заявок.
14. Работает резервное копирование или явно настроен механизм его подключения.
15. Есть журнал административных действий.
16. Опасные действия требуют подтверждения.
17. Работают черновики и безопасная публикация.
18. Есть мониторинг состояния сервисов.
19. Ошибки не раскрывают конфиденциальные данные.
20. Все соединения с сайтом защищены HTTPS.
21. Интеграции не мешают сохранению заявок.
22. Основные сценарии безопасности протестированы.

22. Итоговое требование

Сделай систему, которую можно безопасно использовать в реальном бизнесе.

Не создавай только визуальные элементы безопасности.

Каждая функция должна иметь реальную техническую реализацию.

Если конкретный механизм зависит от тарифа Supabase, хостинга или внешнего сервиса, укажи это в документации и предложи рабочую альтернативу.

Не скрывай ограничения инфраструктуры.

Главный принцип: данные клиентов, доступ к админке и контент учебного центра должны быть защищены, а случайная ошибка не должна приводить к потере всего сайта.
